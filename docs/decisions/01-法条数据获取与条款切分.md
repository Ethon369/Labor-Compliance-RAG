# 01 · 法条数据获取与条款切分

> 阶段 1 数据模块决策记录。对应 `scripts/fetch_laws.py`（抓取 + 解析 + 自校验）。
> 格式约定（CLAUDE.md 第 6 条）：选了什么、备选、为什么、已知取舍。

## 1. 要解决的问题

《劳动法》《劳动合同法》全文要以「法名 / 条号 / 条文」的结构化形式落库，供后续 RAG
检索和引用核验使用。两件事先于代码被卡住：**去哪个源拿权威全文**、**按什么粒度切**。

## 2. 决策一：数据源 —— 官方镜像页，而非单一"官网"或"人人爬的库"

### 选了什么
- 《劳动法》（2018 修正现行版）：商务部法规平台转载页 `policy.mofcom.gov.cn/...id=66953`
- 《劳动合同法》（2012 修正现行版）：新疆人社厅转载页 `rst.xinjiang.gov.cn/...`
- 两部法的「现行性」用**修正条文关键词硬断言**在解析/测试里（15(2)/69/94 条是否已是
  2018 措辞；57/63/66/92 条是否已是 2012 措辞），页面换源或回落旧版会立刻红灯。

### 备选与淘汰原因
| 候选 | 结果 | 原因 |
|---|---|---|
| 国家法律法规数据库 `flk.npc.gov.cn/api/*` | ❌ | 官方最权威，但 `/api/*` 已反爬成 SPA 首页，程序拿不到 JSON |
| 人大网 / 各地政府官网直链 | ⚠️ 不稳定 | 劳动法官网页多处是 **2009 或更早的旧文本**（实测沈阳人社版整页无"市场监督管理部门"等 2018 措辞） |
| 单页爬虫 + bs4 | ❌ 依赖超限 | 锁定技术栈清单外；两个受控页面用标准库状态机更易讲清正确性 |
| 纯手动敲入 / GitHub 文本镜像 | ❌ 可信度与追溯性差 | 无法说明版本与出处，难以追溯 |

**关键教训**：选法律数据源，第一筛不是"能不能访问"，而是"是不是当前修正版"。
镜像页彼此抄，一条错误能传染几十个站。用修正决定公布的条文措辞做哨兵词，
比人眼对目录可靠得多。

## 3. 决策二：解析策略 —— 块级切段 + 状态机，拒绝全文正则

### 选了什么
1. 按块级标签（`p/div/li/td/hN/br`）把 HTML 切成**段落流**，段内剥内联标签、去注释；
2. 逐段跑一个小状态机分类：**章标题 / 条标题 / 正文续段 / 页脚噪音**，累积成条；
3. 页脚用"UI 特征短语"终止（`【TOP】/扫一扫/相关文章/ICP 备案`…），而非裸词；
4. 章标题的正文/目录判据 = **后面紧跟条标题**（目录里的"第X章"后面是另一章）。

### 为什么不是"在全文上正则一把梭"
法律文本有三个特征会坑死全文正则：
- **条款跨多段**：第 2 条的款二常是独立 `<p>`，无条号，需要归属到当前条；
- **页脚与末条相邻**：末条后面的按钮/备案/免责文字是 `<p>`，全文正则无法"停"；
- **条号形态不一**：`第 一 条`（夹空格）、`第一百零七条本法自…`（无空格）。
状态机把"我在哪、下个元素该归谁"显式化了，每条规则都可写单测、可对着页面审。

### 已知取舍
- 解析规则是按**这两个源**校准的；换源要重跑测试校准 STOP/SKIP 词表（已在注释标明"按两源实测"）。
- 抓的是镜像页而非官方库，法律修订后需人工重跑 `fetch_laws.py`（有 `--check` 离线复查）。
- 条款标题行偶尔与正文同行，采用"条号后内容并入文本"，损失了标题与正文的分界——
  本阶段不需要（引用粒度是整条），未来若要做"条内分款引用"需另存原始段落数组。

## 4. 产出形态

`data/raw/{law_id}.json`：`law_id / name / version（沿革行）/ source（URL+抓取时间）/ articles[]`。
`version` 是现行性的人读证据，`source.cross_checked` 预留给人工复核时填对比源。
