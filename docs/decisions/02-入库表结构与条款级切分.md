# 02 · 入库表结构与"条款级切分"

> 阶段 1 数据模块决策记录之二。对应 `scripts/ingest_laws.py`（校验、建表、upsert）。
> 格式约定（CLAUDE.md 第 6 条）：选了什么、备选、为什么、已知取舍。

## 1. 一句话结论

**法律文本的"chunk"就是一条法条**：`articles` 表一行 = 一条，主键
`(law_id, article_no)`，不引入通用 chunk 抽象层。检索时每条自带完整出处，
引用核验不需要再做"这条文本出自哪部法哪条"的拼接猜测。

## 2. 表设计

```sql
laws     (law_id PK, name, version, source jsonb, fetched_at)   -- 每部法一行
articles (law_id, article_no, chapter, text, PK(law_id, article_no))
         -- law_id REFERENCES laws ON DELETE CASCADE
```

- **条款即 chunk**：`(law_id, article_no)` 天然唯一，"按条号精确检索"
  （PRD 验收项）就是主键等值查询，零额外索引。
- **chapter 冗余在每条**：查 36 条立刻知道是第四章，不必 JOIN laws。
- 幂等：`CREATE TABLE IF NOT EXISTS` + `ON CONFLICT DO UPDATE`，整文重跑安全
  （实测重跑 articles 保持 205 行不膨胀）。

## 3. 备选与淘汰

| 方案 | 评价 |
|---|---|
| 通用 `chunks(id, embedding, text, meta jsonb)` 一张表 | ❌ 好处是统一，代价是把"法名/条号"埋进 jsonb，精确检索和引用核验都要反解；法律语料出处分明，不值得 |
| 固定长度（512/1024 字符或 token）重叠窗口切 | ❌ 见下节——会切开法律的最小语义单元 |
| 句子级切分（按。；！断句） | ❌ 法律"款"常独立成句但语义被拆分（如第 2 条款一讲适用范围、款二补一句），引用答案要引整条，句子级召回冗余且难引用 |
| 现在就把 pgvector `embedding vector` 列建上 | ❌ 阶段 2 才有 embedding，先建列=留死代码；演进路径已留：届时 `ALTER TABLE articles ADD COLUMN embedding vector(N)` 即可 |

## 4. 为什么法律文本适合条款级切分（面试核心）

**切分粒度应该由"这个语料被引用的最小语义单位"决定，而不是由模型输入长度决定。**

法律文本的三个特征让它成为条款级切分的完美样本：

1. **条文是语义原子**。第 36 条"每日不超过八小时、每周不超过四十四小时"是一个完整
   规范，第 40 条讲延长工时的加付标准，第 44 条讲终止情形——都是"问一答一整条"。
   读者/系统引用法律时只会说"根据《劳动法》第 X 条"，从不说"第 X 条后半句"。
2. **条文自带唯一地址**。`(law_id, article_no)` 是全世界通用的定位系统，
   RAG 的引用环节（PRD 核心流程里的"引用核验"）因此变成主键查询，零歧义。
3. **长度天然适配**。两部法条文平均 100–200 字，bge-m3 等 embedding 模型窗口
   （数千 token）轻松容纳，**几乎不需要再切**，也就不存在"截断丢语义"的问题。

### 对比：固定长度切分的缺陷（面试必讲）

以"每 512 字硬切、80 字重叠"为例，对法律文本会出三种事故：

- **切断语义原子**：第 36 条刚好落在 500–560 字窗口边界上，"……平均每周工作时间
  不超过四十四小"和"时的工时制度"被分进两个 chunk。embedding 阶段，两半的向量都
  是"残句"，谁都召不回"劳动法 44 小时"这个完整问题；
- **引用错位**：答案想引"第 36 条"，但对齐后 chunk 的 `meta.article_no` 只能是
  "起始条号 36"或"37"，下游"引用核验"要么错引要么需要额外算法把碎片拼回原文；
- **检索噪声**：同一问题会同时命中残句 chunk 的两半，rerank 面对近乎重复的候选，
  召回数被无意义结果稀释。

### 面试追问："chunk size 到底怎么定？"

别答"512 或 1024"。正解是分层的：

1. **先找内容边界，再谈数值**。chunk 是"检索单元"不是"token 预算"。Markdown 按
   标题、论文按段落、代码按函数、法律按条款。法律条款级恰好还同时满足
   "引用粒度 = 检索粒度"。
2. **固定窗口只是兜底**。只有当文本没有可靠边界（如长聊天记录）才退回
   "固定 token + 重叠"。法律语料不在此列，所以本项目压根没设字符常数——
   这在架构图上是个能主动解释的点。
3. **数值上限由 embedding 模型定，不是拍脑袋**。真要说数字，是"最长条款不能超
   bge-m3 上下文"，超了才在该条内部二次切分（本项目两部法没有超的）。
4. **最终用评测集验收，不用直觉**。PRD 的 50 条评测集 + `eval/` 脚本会在检索阶段
   对比"条款级 vs 窗口级"的召回率——这是"粒度选对了"的证据，不是嘴说。

## 5. 已知取舍

- 不含 embedding 列与向量索引，阶段 2 加（演进路径见上）。
- 不含全文检索列（tsvector/BM25 倒排在阶段 2 与混合检索一起做，避免现在造两张表）。
- `chapter` 为可空展示字段；若某源正文无章标题，检索与引用不受影响。
- 整条条文存入 text（跨段以 `\n` 连接保留"款"边界），未做"款级"拆分——
  见决策 01 第 3 节取舍。
