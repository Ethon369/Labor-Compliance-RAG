# 03 · 混合检索：pgvector 向量路 + BM25 + RRF 融合

> 阶段 2 检索模块决策记录。对应 `app/rag/`（tokenizer/embedder/vectorstore/bm25/
> fusion/retriever）与 `scripts/backfill_embeddings.py`。
> 格式约定（CLAUDE.md 第 6 条）：选了什么、备选、为什么、已知取舍。

## 1. 一句话结论

**检索走两条路、各取候选、用 RRF 按"排序位置"融合成最终排序**：
向量路（pgvector `<=>` 余弦近邻）负责语义相近、词面不同的召回；BM25 路（rank-bm25）
负责词面精确、术语严苛的召回。两路各自的 top-N 只是候选，谁排前面交给融合，不交给
任一路独裁。数据库表 `articles` 由此从"条款级语料"升级为"带 embedding 的检索库"。

## 2. 本阶段实现的结构

```
                    query
                     │  embed(query)         tokenize(query)
        ┌────────────┴────────────┐
   向量路 PgVectorStore        BM25 路 Bm25Index
   (articles.embedding,      (rank-bm25 内存倒排,
     <=> 余弦, SQL 端)          词元=汉字滑窗二元组)
        └────────────┬────────────┘
           各 top-candidate_k 个 (law_id, article_no)
                     │  rrf_fuse([vec_keys, bm_keys])
              RRF 融合 → 前 top_k → RetrievalResult
```

部件划分（每个都可单测）：
- `tokenizer.py`：汉字滑窗二元组 + ASCII 词，零第三方依赖（替代 jieba，见 §3）；
- `embedder.py`：`Embedder` 协议 + 两个实现——离线 `HashEmbedder`（确定性词元哈希
  稠密向量）与真 `SiliconFlowEmbedder`（bge-m3，OpenAI 兼容 /embeddings）；
- `vectorstore.py`：pgvector 就绪（扩展+列）、全量语料、写向量、`<=>` 余弦 top-k；
  向量以 `format_vector` + `%s::vector` 转型传入，**不引 pgvector 的 Python 适配包**；
- `bm25.py` / `fusion.py`：稀疏路与 RRF 纯函数（fusion 只吃排序、不吃分数）；
- `retriever.py`：编排 + `build_retriever(Settings)` 组装点。

## 3. 备选与淘汰

| 方案 | 评价 |
|---|---|
| 单路：只做向量检索 | ❌ 法律条文用词高度固化，"解除劳动合同""经济补偿"等说法有准词面；纯语义向量对精确表述反而可能召回"意思相近但条文无关"的内容 |
| 单路：只做 BM25 | ❌ 用户口语"公司拖欠工资不给怎么办"与法条原文"克扣或者无故拖欠工资"存在词面鸿沟，无同义/词序泛化（实测 vector 路能召回，见 §6） |
| 加权平均两路分数 | ❌ BM25 得分（对数词频叠加，可达几十）与余弦（[0,1]）量纲根本不可比，权重无物理意义、每换一个 embedding 都要重调 |
| **RRF 融合**（选中） | ✅ 只吃"排序位置"：任何路的内部排序都可比，跨路分数不可比的问题被绕开；无超参（只一个 k=60，论文标准值），鲁棒 |
| 向量路放内存（numpy 余弦） | ❌ 本机已有 pgvector 容器；放进 PG 才符合"锁定技术栈"，且 SQL 近邻是面试可讲的真 ANN 形态（量级上来加 HNSW 索引即可） |
| 引 `pgvector` Python 适配包 | ❌ 清单外依赖。psycopg 参数绑定 + `%s::vector` 显式转型已足够，转型交给 PG 端 |
| 引 jieba 分词 | ❌ 清单外。汉字滑窗二元组无词表即可切"加班费→加班/班费"，BM25 的 idf 会自然压低高频噪音 |
| 真 bge-m3 走本地（sentence-transformers 等） | ❌ 引入 torch 系重依赖且本机无 key/无网；改为 `SiliconFlowEmbedder` 走 API，接口与占位向量同一协议，之后有 key 一换即得 |
| 本阶段就把 bge-reranker 语义精排接上 | ❌ rerank 是检索的**下一块**（候选→精排是不同层）；先验证两路召回与融合，避免一次接太多变量 |

## 4. 为什么 RRF 是"只吃排序位置"——公式直觉

$$score(d) = \sum_{\text{路}} \frac{1}{k + rank_d(d)},\quad k=60$$

三条性质，逐条讲清：

1. **与分数解耦**。BM25 分数和余弦距离没有共同量纲，加权平均没有物理意义；但"某条
   条款在第 X 路排第几名"这个事实在任何路内部都是成立的、可比的。RRF 扔掉分数、
   只保留这个弱得多的信息——**放弃精确性，换取跨路的可比性**。
2. **位置越高，边际收益越大（但对前几名不敏感）**。`1/(k+rank)` 是 rank 的倒数型：
   top1 贡献 ≈ 1/61 ≈ 0.0164，top10 ≈ 1/70，top100 ≈ 1/160。靠前的位置值钱，但
   top1 和 top2 只差约 0.00027——不会因为某路微小的分数抖动就剧烈改判（比直接拿
   分数排序稳）。这正是面试爱问的点：**RRF 对"每路给分尺度"完全不敏感，代价是对
   "某路自身排序噪声"也只做了平滑而非消除**。
3. **一个文档要在某路出现才有贡献**。只在向量路出现、被 BM25 完全漏掉的条款，融合
   后仍能保留（1/(k+pos) 那一路的贡献仍在）；两路都命中的文档天然累积两份分数——
   这是"两路共识"被奖励的机制。

## 5. 关键技术取舍

- **embedding 列维度 = 1024，对齐 bge-m3**：决策 02 说"届时 ALTER 加列"，现在落地为
  `ALTER TABLE articles ADD COLUMN embedding vector(1024)`。占位向量与真 bge-m3 同维，
  以后换真模型只重灌数值（`backfill_embeddings.py --force`），**不用重建表**。
- **占位向量的诚实定位**：`HashEmbedder` 是"词元集合的确定性稠密投影"（md5 投到固定
  维 + 词频 + L2 归一），只有词面重叠语义，召回能力≈BM25 又比 BM25 多一层哈希噪声。
  它的职责是让 **pgvector 算子 / SQL / 融合 / 全链路离线可跑、可复现、可测试**；真正
  的词面外语义（同义改写、语序无关）等 bge-m3 上线才有。
- **候选生成与最终排序分离**：每路取 `candidate_k=20` 当候选，RRF 后只取 `top_k=8`。
  单路直接 top-8 定生死的话，融合就没机会把"两路都第 11 名"的共识条款抬上来。
- **BM25 语料进程内缓存**：205 条全量进内存一次，之后每查询只走倒排打分；本阶段数据
  静态（仓库已提交 raw JSON），语料变更需重建——规模量级上来再评估外置索引。
- **每查询短连接**：`PgVectorStore` 每次操作开连接即关，零状态、好测试；FastAPI 阶段
  换连接池（app/core 依赖注入层的事，检索层接口不变）。
- **SQL 全部参数绑定**：向量以绑定参数 `%s::vector` 传入；`LIMIT`、`WHERE` 同样占位。
- **测试分工**：离线单测（切词/embedding/RRF/BM25/用内存替身验证编排）不碰库；
  `@pytest.mark.db` 集成测试真连 labor-pg 验证"pgvector 路 + BM25 路 + 融合都命中
  手挑的 (查询, 应得条款) 对照"，连不上自动 skip。全量 51 用例通过
  （fetch/ingest 32 + rag 离线 14 + 真库 5）。

## 6. 已知取舍与教训（真实数据）

- **验收查询刻意与法条原文同词**：占位向量只有词面语义，所以集成测试的 4 组查询写成
  与原文强重叠的"法律相关问法"。真 bge-m3 之后，同义/口语改写才应被召回到同一条款。
- **弱向量路会拖累融合（实测）**：口语查询"公司拖欠我的工资不给怎么办"，BM25 路
  top1 = 劳动法 #50（正确，条文含"克扣或者无故拖欠劳动者的工资"），而占位向量路
  top1 = 劳动法 #44（加班费条款，漂移——查询的"不给""怎么办"等词被哈希成随机噪音，
  泛化的"工资/支付"高频词主导了相似度）。RRF 假设"每路都基本及格"，一路差会把融合
  带偏。教训写进两条：①混合检索的前提是**每路各自够强**，不能指望融合兜底；②占位
  向量阶段的合理用法是向量路作为补充召回，不能喧宾夺主。
- **短连接无连接池、BM25 全内存**：205 条规模可接受，是"先跑通再谈 scale"的取舍，
  与决策 02 同思路——不为还没发生的问题建抽象。
- **未建向量 ANN 索引**：pgvector 的 HNSW/ivfflat 在行数上来后加（本阶段 205 行顺序扫
  足够，索引是下一阶段的优化决策点）。

## 7. 演进路径（给下一块留的接口）

- rerank：`retriever` 候选后接 bge-reranker 语义精排（本地或硅基流动），替换/叠加 RRF；
- API 层：`build_retriever` 已把组装点备好，FastAPI 路由直接依赖注入即可；
- embedding 提供方：`EMBEDDING_MODE=siliconflow` + 填 key → `--force` 重灌 → 不用改
  检索层任何代码（接口协议不变）。
