# 04 · Rerank 精排与检索评测

> 阶段 3 决策记录。对应 `app/rag/reranker.py`、`retriever.py` 的精排管道、`eval/`（50 问评测集 + Recall@k/HitRate@k 指标 + runner 对比表）。
> 格式约定（CLAUDE.md 第 6 条）：选了什么、备选、为什么、已知取舍。

## 1. 一句话结论

**检索分两段：RRF 只负责把两路候选"融合成同一把尺子"，rerank 负责在融合后的更大候选池上做二次精排。** 评测框架用 50 条劳动争议场景问答 + 双指标（Recall@k / HitRate@k）量化三档配置的差距，并把"为什么加 rerank 反而超过最好的单路"讲成可复现的数字。

离线占位实测（top-8，50 问）：

| 方法 | Recall@8 | HitRate@8 |
|---|---|---|
| 纯向量 | 0.635 | 0.679 |
| 纯BM25 | 0.789 | 0.830 |
| 混合(RRF) | 0.742 | 0.793 |
| **混合+rerank** | **0.815** | **0.849** |

反常现象（讲解重点）：**混合(RRF) < 纯BM25，但加 rerank 后全场最高。** 原因见 §6。

## 2. 本阶段实现的结构

```
             query
              │
    ┌─────────┴──────────┐
  向量路              BM25 路
 (pgvector 余弦)      (rank-bm25)
    └─────────┬──────────┘
      各取候选(默认 20)  →  rrf_fuse 融合 → 取前 rerank_pool(默认 30)
              │   reranker.score(query, pool_texts)   ← 精排
              ▼  按精排分降序、稳定排序
         取前 top_k(默认 8) → RetrievalResult
```

关键设计：

- **池是"融合后"的 30，不是 top-8**。精排只对已入围候选排序，不负责把没召回的捞回来（召回阶段的责任在第 1 段）；池 > top_k 是因为精排的用武之地就是"把第 20 名的正确条文升到第 3 名"。实测数据（§6）证明这个池给得值。
- **`search(use_rerank=True/False)` 一个实例两条路径**：评测脚本在同一 retriever 上开关 rerank，对比的是"同一套候选池里有没有二次精排"的边际影响，不是两套参数调出来的结果——这是干净对照组。
- **rerank 与 embedder 同套路**：`Reranker` 协议 + 两个实现——离线 `TermOverlapReranker`（query 词元在 doc 中的覆盖率）与真 `SiliconFlowReranker`（bge-reranker-v2-m3，`/rerank` 端点，urllib 零新增依赖）。缺 key 当场报错，不静默降级（与 embedder.py 一致）。

## 3. 备选与淘汰

| 方案 | 评价 |
|---|---|
| 直接用 rerank 分数替代 RRF，不做融合 | ❌ 那要拿全部 205 条去精排，每查询 205 次成对打分；rerank 是 O(pool × 模型推理)，pool 必须来自一个便宜的初筛，RRF 融合天然就是那个初筛 |
| rerank 只精排 top-8 | ❌ 池太小：精排排的是"已可见的 8 条"的顺序，第 9 名以后的好条文根本没有翻身机会（正是我们实测发现 RRF 融合后正确条文沉到 8 名外的问题） |
| **RRF 融合取 30 名进精排**（选中） | ✅ 初筛便宜（融合只是排序位置算术）、精排有选择余地，一次查询 30 次成对打分（205 条全量精排的 1/7） |
| 把 rerank 做进 SQL/索引 | ❌ 语义精排是跨文档的成对模型推理，PG 端没有这个能力；保持"SQL 端召回、Python 端精排"的两段分层 |
| 引 transformers 本地跑 bge-reranker | ❌ 引入 torch 重依赖；本机无 key/无网。API（硅基流动）同一协议，有 key 一换即得 |
| 评测只算命中率（Hit Rate） | ❌ 单指标会漏掉"多标注问题找全了没"（见 §5），双指标才覆盖"首次体验"和"查全"两个不同视角 |

## 4. 为什么 rerank 延迟和收益要一起谈

rerank 的代价是**每查询新增 pool 次成对打分**，且**不能复用**（embedding 可以预计算存 PG，rerank 是查询时对候选动态成对打分）：

- 延迟 = 初筛（两路检索 + 融合，毫秒级） + rerank（pool 次模型调用，约 pool × 30–80ms，取决于 provider）。
- pool 翻倍 → 精排延迟近翻倍，但 Recall 边际收益递减（§6 实测：pool 30 已经把 8 名外的正确条文都含进来了，再大只多打不太可能翻身的条文）。
- 取舍结论：**top-k 固定时，pool 是"延迟 × 召回上限"的旋钮**。演示场景宁可让 pool 大一点换正确率；生产场景（实时问答）会按 SLO 收紧 pool，或从 30 降到用户可感知的延迟内。
- 为什么 rerank 的延迟"值"：精排是唯一能提升**排序质量**的环节——两路融合只保证"正确条文在池里"，只有 rerank 保证"正确条文出现在用户看到的 top-k 里"。召回率是上限、排序才是用户感知的分界线。

## 5. 两个指标的定义与分工（核心要点）

- **Recall@k**：对每条问题，`top-k 中命中标注数 / 标注总数`，再对所有问题求平均。度量"用户想要的东西，系统找回了多大比例"。**依赖多标注**（一条问题标注多条应命中条款）——单标注问题 Recall 只有 0/1 两值，区分度差，所以 50 问里有约 1/3 是多标注。
- **Hit Rate@k**（又叫 Success@k）：`top-k 至少命中一条标注的问题数 / 总问题数`。度量"用户在 k 条结果里能不能看到至少一条有用的"。对单条标注的问题也有效，贴近"首条体验"。
- 分工：**Rec = 查全率，Hit = 首条命中率**。只报 Hit 会掩盖"找回来了一条但主要条款没找着"；只报 Rec 会掩盖"大部分用户的问题根本没出现在可见结果里"。
- 与经典 Precision@k 的区别：本例标注是"应该命中"而非"每条结果都该有用"，Precision 无法定义（法律条文检索天然是"宁缺毋滥"场景，错误的 top-k 条目会直接误导引用），所以用 Hit Rate 代替 Precision 做"结果质量"面。

## 6. 为什么混合(RRF)打不过纯BM25，加rerank却全场最高（实测解读）

这个现象不是 bug，是**三步各司其职**的教科书演示，按顺序看：

1. **占位向量路的"冗余假召回"**：本评测用 `HashEmbedder`——它是词元集合的稠密投影，语义能力≈词面匹配，与 BM25 高度冗余。向量路 top-20 里混进了大量"词面沾边但不相关"的条文（md5 碰撞和共现词噪音）。
2. **RRF 融合吃进了噪音**：RRF 对两路候选一视同仁按位置计分。向量路的噪音条文在融合里占了位置，挤掉了 BM25 里排名更深（比如 6–15 名）的正确条文——所以混合的 top-8 反而劣于纯 BM25 的 top-8。
3. **rerank 把"对"的条文从深水位拉回可见区**：融合出的 top-30 池里**依然包含**被挤掉的好条文（它们只是排到了 9–30 名）。`TermOverlapReranker` 按"查询意图词在条文中的覆盖率"重新打分——这正是"这条例文到底回答没回答用户的问题"的直接度量——把第 12 名的正确条文升到第 2 名。

这三点合起来解释了 rerank 的价值模型：**召回（把候选找全）和排序（把对的排前）是两个正交环节**；两路融合负责前者（保证池里有货），rerank 负责后者（保证货出现在第一屏）。离线占位在"语义"上弱，恰好把这两段的职责差异放大了——如果直接上真 bge-m3 + 真 bge-reranker，向量路会提供更独立的召回，混合的收益会更直观，但"rerank 提升排序"的机制不变（详见 PRD 的后续评测规划）。

## 7. 评测集设计（为什么不随机抽 50 条）

- **按法条章节分层**：工作时间/工资/劳动合同订立/解除终止/女职工与未成年工保护/劳动争议程序/劳务派遣与非全日制，每层挑高、中、低频条号——既考常见问题召回，也考冷门条号有没有死角。
- **口语化发问**：不用法条原文当 query（那是作弊——检索器只需要词面匹配）；模拟用户真实咨询措辞（"公司能收我押金或者扣我身份证吗"），检验同义表述下的召回鲁棒性。离线占位的向量路在这里吃亏，正好暴露"需要真 embedding"的替换理由。
- **标注是 (law_id, article_no) 集合**：一条问题可标多条例文（如"拖欠工资"标劳动法 50 + 91），Recall 才有区分度（§5）。
- **自校验**：问题数 ≥ 50、无重复、标注必存在且合法、两部法律都被覆盖——评测集本身有一组 pytest 防腐坏。

## 8. 已知取舍

1. **离线占位 rerank 的语义上限**：词元覆盖率只认词面，不认同义改写（"发薪"vs"支付工资"认不出）。它是确定性、零依赖的管道打通器；真 bge-reranker 一换即得，接口不变。
2. **标注依赖人工**：50 问的 gold 标注是对照两部法条原文逐条人肉核对的（自校验只能查格式，不能查法律正确性）；将来扩充评测集时，标注是主要人力成本。
3. **poll 固定 30，未做 pool 扫描**：评测只对比了"有/无 rerank"，没扫 pool∈{10,20,30,50} 的 Recall 曲线。pool 的边际收益曲线（§4）值得后续补一组数据，但当前 50 问量级下 30 已经全包正确条文。
4. **单轮检索评测**：本阶段评测的是检索层（不接 LLM 生成）。端到端答案质量（引用准确率、幻觉率）是阶段 4 测 LLM 链路时的事，检索层指标是它的前置输入。
