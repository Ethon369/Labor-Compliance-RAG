# 09 · 拒答边界与 LLM 接入

> 阶段 8 决策记录。对应 `app/agent/nodes.py` 的 `make_verify_node`、`app/agent/graph.py`
> 的 `build_agent`/`build_agent_from_config`、`tests/test_agent.py` 的 pass/rule 模式测试。
> 格式约定（CLAUDE.md 第 6 条）：选了什么、备选、为什么、已知取舍。

## 1. 一句话结论

**Agent 的"要不要拒答"成为可配置的边界（`verify_mode`），且默认一律 `pass`（命中即答）——
offline 模板和真 LLM 都不再走规则拦截；拒答判断分别交给"模板不产生新结论"的天然安全、
LLM system prompt 的自我约束，规则核验（`rule`）降级为可选的测试/特殊场景后备。**

## 2. 背景：为什么原先的拒答会误杀

原设计（决策 05）：`verify` 节点用 `CitationVerifier` 纯规则核验——只看 **top-1 条文**对
查询意图词的**覆盖率**（双字词元重叠 / 查询词元数），阈值 0.3，不达标走 `refuse` 支路。

实测"公司拖欠我加班费怎么办"：

- 检索 8 条，top-1《劳动合同法》第31条（"……安排加班的，应当按照国家有关规定向劳动者支付加班费"）
  ——条文内容正中问题，但覆盖率只有 **0.20/0.3**。
- 原因：查询词元 10 个（`公司/司拖/拖欠/欠我/我加/加班/班费/费怎/怎么/么办`），其中
  `怎么/费怎/么办` 是口语尾缀碎片，条文只覆盖 `加班/班费` 等 2 个语义核心词 → 0.2。
- 结论：**覆盖率度量对"口语长查询 vs 短规范条文"天生不匹配**。top-1 + 0.3 是赌命：
  赌"恰好第一条条文覆盖 >=1/3 查询词"。规范条文往往做不到，误杀率极高。

已验证的无效备选（实测数据）：

| 改法 | 结果 |
|---|---|
| 降阈值 0.3 → 0.15 | 测评 50 问通过率 31/53 → 46/53，但边界更松、误答风险上移 |
| top-k 取最大覆盖率 | 本例 max 仍 0.20（8 条命中里最高就 0.20），无用 |
| 停用词净化查询词元 | 0.20 → 0.22，接近但不够 |

## 3. 选中的方案：verify_mode 两态，默认 pass

```
make_verify_node(verifier, mode="pass"|"rule")：
- "pass"：bool(hits)——有命中即可答，空命中仍拒答
- "rule"：CitationVerifier 原逻辑（top-1 覆盖率阈值）

build_agent(..., verify_mode="pass"|"rule")  # 默认 "pass"
build_agent_from_config：offline / llm 一律 verify_mode="pass"
```

为什么两条模式都默认 pass：

1. **offline 模板本就不设防**：`TemplateAnswerer` 只拼条文原文、不产生引用断言之外的
   新结论（无幻觉风险），拦截它是纯挡路——演示/CI 时任何正经问题都被拒。
2. **真 LLM 自己能拒**：`_ANSWER_SYSTEM_HEAD`（protocol.py）已写明"如果条文与问题无关或
   不足以回答，直接说「无法提供明确结论」"。把拒答判断交给 LLM：
   - 规则阈值是**固定一刀切**，覆盖率度量天生误杀（§2）；
   - LLM 看的是**语义**，能识别"条文真不相关"；且 LLM 拒答输出人类可读的原因。
3. **空命中仍然拒答**：检索零命中时没有依据可以引用，pass/rule 都拒，不浪费 LLM 调用。
4. **rule 保留为后备**：给测试验证拒答链路用（`client_refuse`/`_invoke` 显式传 `"rule"`），
   也允许将来用户手动启用规则兜底。

## 4. 与 LLM 接入的关系

- `LLM_MODE=offline`：`PassThroughRewriter` + `TemplateAnswerer` + pass——零 key 全链路可演示。
- `LLM_MODE=llm`：`LLMRewriter`（润色查询）+ `ToolCallingAnswerer`（真 LLM + 经济补偿金
  计算器 function calling）+ pass——检索给依据、LLM 组织回答和拒答判断。

实测（硅基流动 Qwen3.5-4B）同一问题两种模式：

| 模式 | 回答 |
|---|---|
| offline | 模板拼 8 条条文原文罗列（机械但可演示） |
| llm | 结构化回答：法定义务（31条）→ 支付令（30条）→ 逾期加付赔偿金（85条）→ 法律责任（《劳动法》91条）→ 维权建议 |

## 5. 已知取舍

1. **LLM 拒答依赖模型自我约束**：模型可能"条文不足以回答"时不拒而强答（幻觉）。原规则
   核验就是为防这个——放弃规则 = 接受模型判断为准。对本项目（辅助参考工具 + 免责声明）
   风险可控；若未来严格合规场景，重新启用 `rule` 或将 LLM 拒答原因回溯检查即可（一行参数）。
2. **覆盖率规则的教训保留**：`rule` 模式仍可启用，但已知对口语短查询误杀（实测 22/53
   拒答）。若将来细化规则，方向是：按语义词（非双字词元）+ 长条文窗口 + 多命中并集，而不是调阈值。
3. **测试里的拒答链路仍靠 rule 显式指定**：test_api 的 `client_refuse` 和 test_agent 的
   `_invoke` 都传 `verify_mode="rule"` 保住"top-1 无关 → 拒答"的断言——这是语义说明，
   不是线上默认行为。
4. **LLM 延迟/成本进演示链路**：llm 模式每次提问都调 API（改写 1 次 + 回答 1 次），
   offline 零成本。演示时若想避开网络抖动可用 offline 模式预热。
