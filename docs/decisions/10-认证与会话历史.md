# 10 · 认证与会话历史

> 阶段 9 决策记录。对应 `app/api/auth.py`、`app/api/routes.py` 的 `/chat/history/mine` 与
> 落库逻辑、`app/main.py` 建表、`app/static/index.html` 登录弹窗与侧边栏真历史、
> `tests/test_auth.py`。格式约定（CLAUDE.md 第 6 条）：选了什么、备选、为什么、已知取舍。

## 1. 一句话结论

**自制认证：PBKDF2-SHA256 密码哈希 + HMAC-SHA256 签名 token（无第三方库）。
登录用户的每问一答持久化到 PostgreSQL `chat_history` 表；游客照常可问但历史只进
内存（关页即没）。会话历史按用户隔离，登录后侧边栏显示「自己的历史」并可回看。**

## 2. 目标

- 换更快的 LLM（阿里云百炼 qwen-plus，替换原来偏慢的硅基流动）——见 §6。
- 历史对话可长期保存 + 按用户隔离：登录才能看自己之前的问答。
- 游客可以问、可以临时存，但关页面就没了（对齐产品定位"演示项目，不做强登录墙"）
- 全程零新依赖（CLAUDE.md 规则 1 锁定清单；认证用标准库实现）。

## 3. 选中的方案

### 认证
| 环节 | 实现 |
|---|---|
| 密码哈希 | PBKDF2-HMAC-SHA256，迭代 10 万次，随机盐，`salt$digest` 存储 |
| 校验 | `hmac.compare_digest` 防时序侧信道；畸形存储一律判 False（不 500） |
| token | `<base64url(payload)>.<hmac-sha256 签名>`，payload 含 uid + exp(7 天) |
| 令牌接口 | `POST /auth/register`、`POST /auth/login`、`GET /auth/me` |
| 入口 | 前端侧边栏左下角"登录/注册"，token 存 localStorage，fetch 带 `Authorization: Bearer` |

### 历史
- 新表 `users(id, username unique, password_hash)`、`chat_history(id, user_id FK, question, answer, citations json, created_at)`。
- `lifespan` 启动 `ensure_user_schema()` 幂等建表。
- `POST /chat`：解 token 得 uid → 问答落到 `chat_history`；游客跳过。
- `GET /chat/history/mine`：带 token 读该用户最近问答。
- 侧边栏登录后渲染真历史，点击回看完整回答 + 引用；新增「新对话」清空当前消息区。

## 4. 备选及为什么不选

| 备选 | 为什么不选 |
|---|---|
| 引 JWT/PyJWT | 违反锁定清单"零新依赖"；自制 HMAC 签名原理三段话能讲清，面试更好讲 |
| 明文/简单哈希存密码 | PBKDF2 加盐是标准廉价防线，不加白不加 |
| 纯前端 localStorage 存历史(方案B) | 关浏览历史就消失、不能跨设备、不能按用户隔离——不符合"长期保存"诉求 |
| 只接内存 /chat/history(方案C) | 服务重启即丢，不是"持久会话历史" |
| 用第三方认证(邮箱/微信登录) | 演示项目引入外部服务过重，用户无邮箱验证诉求 |

## 5. 已知取舍

1. **自制 token 非标准 JWT**：结构（payload.signature）与 JWT 相近但未走标准库/协议，
   语义自洽但不可与既有 JWT 生态互操作。对单机演示够用；接前端鉴权网关时再换标准 JWT。
2. **无刷新/撤销机制**：token 7 天有效期内不可主动踢下线（demo 可接受；严格场景需
   刷新 token + 黑名单）。
3. **游客历史在内存**：`app.state.history` 列表，重启清空——有意为之，与产品定位对齐。
4. **落库失败静默忽略**：DB 抖动不阻断回答本身（回答是主、落库是次）。
5. **密码最小长度 4**：演示友好，非强合规；生产应上调长度+加强度校验（一行约束可改）。
6. **`AUTH_SECRET` 有 dev 默认值**：.env.example 注释了"生产必须覆盖"；当前默认值仅
   本地演示用，不应推到生产裸跑。

## 5.5 多轮会话增强（阶段 10 后补）

初版每条问答独立落 `chat_history`，侧边栏只是"问题列表"——会话感弱。后改为真会话：

- 新表 `chat_sessions(id, user_id, title, updated_at)` + `chat_messages(id, session_id, role, content, citations)`。
  role 限 user/assistant；citations 存 JSON（assistant 消息带引用，供回看时渲染）。
- `POST /chat`：请求带 `session_id` → 校验归属并取该会话最近若干轮消息作为 history 注入
  answer 节点（prompt 里前插 user/assistant 消息，让 LLM 能承接"超过这个期限怎么赔偿"式追问）；
  不带 `session_id` → 自动建会话（标题=问题前 20 字），并在 done 帧回传 `session_id` 供前端记住。
- `GET /chat/sessions`：会话列表（倒序）。`GET /chat/sessions/{id}/messages`：某会话全部多轮消息。
- 游客无 DB 会话：前端内存维护 `guestHistory`，随请求 `history` 字段上传，关页即没。
- 前端：侧边栏=会话列表；点开=拉全量消息回显多轮并进入该会话续问；「新对话」重置上下文。

取舍：
1. **检索不回看历史**：多轮上下文只喂 answer（LLM 组织回答），rewrite/retrieve 仍只看当前问题。
   对法条 RAG 够用——追问多指向法条本身；真正"检索要翻上下文"留给 v2（rewrite 时拼历史）。
2. **上下文截断**：只取最近 6 轮喂 LLM，游客只存最近 12 条——防 prompt 膨胀，演示量级足够。
3. **历史隔离**：会话归属校验在读取层（`load_session_messages` 带 user_id，非本人返回空→404）。
4. **旧的 `chat_history` 表与 `/chat/history/mine` 接口保留**：向后兼容，未删。

## 6. LLM 供应商迁移（顺带）

- 原 `LLM_BASE_URL=https://api.siliconflow.cn/v1` + `Qwen/Qwen3.5-4B` 响应偏慢（单次近 60s，
  偶发撞 60s 超时 → 报"read operation timed out"）。
- 新 `LLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1` + `qwen-plus`
  （阿里云百炼 OpenAI 兼容接口）。**代码零改动**——`protocol.py` 本来就是 OpenAI 兼容
  `chat/completions`，只换地址 + 模型名。
- 未动 `embedding/rerank`（仍 offline 占位，见决策 03）。LLM 单独走 dashscope。
