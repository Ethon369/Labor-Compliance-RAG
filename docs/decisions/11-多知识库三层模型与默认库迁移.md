# 11 · 多知识库三层模型与默认库迁移

> V2.1 决策记录。对应 `app/kb/schema.py`、`scripts/migrate_default_kb.py`、
> `app/kb/store.py`、`tests/test_kb_schema.py`。格式约定（CLAUDE.md 第 6 条）：
> 选了什么、备选、为什么、已知取舍。

## 1. 一句话结论

**知识库从"一张 articles 表装 205 条法条"升级为 `kb → documents → chunks` 三层；
内置《劳动法》《劳动合同法》迁移成默认库（kb_id=1）里的两个文档、205 个切片，
与用户上传的文档走同一张表、同一套检索代码。articles 表保留，降级为迁移数据源。**

## 2. 目标

- 支持多用户各管自己的知识库（V2.2/V2.3 落地），上传文档与内置法条同等待遇。
- 检索路径唯一：不再有"法条专用逻辑"和"文档专用逻辑"两套。
- 引用能定位到"哪个文档的哪一段、第几页"，而不只是"哪部法第几条"。
- 现有 50 问评测集继续可用，不重标注。

## 3. 选中的方案

### 表结构（`app/kb/schema.py`，单事务幂等建表）

```sql
kb(id, name, description, owner_id→users, is_public, chunk_size, chunk_overlap,
   embed_model, doc_count, chunk_count, created_at, updated_at)
documents(id, kb_id→kb CASCADE, title, source_type, source_law_id, file_size,
          status(pending|parsing|embedding|ready|failed), error, chunk_count, ...)
chunks(id bigserial, kb_id→kb CASCADE, doc_id→documents CASCADE, seq, page, heading,
       content, char_count, content_hash, UNIQUE(doc_id, seq))
```

- **为什么三层**：删单个文档只删它的切片、不牵连整库重建；文档级处理状态可追踪；
  引用可定位到文档+段+页。
- **`documents.source_law_id`**（相对方案文档的新增列）：只有内置法律迁移来的文档有值。
  它是 eval gold 映射与"引用显示第 N 条还是第 N 段"的权威来源，避免把映射硬编码进代码。
- **`chunks.content_hash`**（新增列）：重传/reindex 时未变的片跳过重算 embedding。
- **`chat_sessions.kb_id` 用 `ON DELETE SET NULL`**：否则删除一个被历史会话引用过的库会
  被外键阻断；SET NULL 后该会话检索自动回退默认库。
- `users.role` 列也在本文件加（CHECK user/admin），供 V2.2 权限使用。

### 默认库迁移（`scripts/migrate_default_kb.py`，幂等可重跑）

读 `articles` 表（不依赖 data/raw 的 JSON 文件，Docker 镜像里不一定有）：

| 规则 | 值 |
|---|---|
| 库 | `kb(id=1, '劳动法知识库', is_public=TRUE, owner=admin)` |
| 文档 | 每部法一个 document，短名取法名去掉"中华人民共和国"前缀 |
| seq | `= article_no`（**可逆**，eval 翻译只做 law_id→doc_id） |
| heading | `= article.chapter`（章名即该条最近的上级标题） |
| page | NULL（法条无页码） |
| 写入 | `ON CONFLICT (doc_id, seq) DO UPDATE`，整文重跑安全 |
| 自校验 | 末断言 2 文档 / 205 切片，不达标非 0 退出 |

### 评测集身份翻译（`eval/compat.py`）

gold 标注仍是法律语义的 `(law_id, article_no)`，**不重标注**——重标既费人力、又让历史
指标失去可比性。在评测入口用 `law_to_doc()` 把 `law_id` 翻成 `doc_id`，`seq == article_no`
保证 `article_no` 原样可用。`eval/questions.py`、`eval/metrics.py`、`tests/test_eval.py`
的指标断言一行未改。

## 4. 备选及为什么不选

| 备选 | 为什么不选 |
|---|---|
| 保留 articles 表，上传文档另走新表 | 检索/融合/引用/LLM 拼文要维护"法条身份 + 文档身份"两套分支，长期维护成本高；引用定位的面试叙事也不再统一 |
| 一张 `chunks(id, embedding, text, meta jsonb)` 大表 | 决策 02 已淘汰过：法名/条号埋进 jsonb，精确检索与引用核验要反解，查询与索引都吃亏 |
| 把 205 条按固定长度重新切分 | 法律天然按条组织，一条=一个完整语义单元；固定长度会把一条切两半或混两条，引用变模糊（决策 01/02） |
| 重标注 50 问评测集 | 人力成本 + 历史指标不可比；翻译层只需 ~40 行 |
| 给 articles 表加 kb_id 复用旧表 | 法条没有页码/标题层级/处理状态这些文档属性，硬塞会得到一堆恒为 NULL 的列 |

## 5. 为什么这样最好

**"换数据层、不换内核"**：检索编排、RRF、rerank、Agent 拓扑、function calling 全部不动，
只把"语料单元"从法条换成切片。收益在 V2.1 就被量化验证了——迁移后重跑评测，
四个配置的 Recall@8 / HitRate@8 与迁移前**逐位相同**（0.6352/0.6792、0.7893/0.8302、
0.7421/0.7925、0.8145/0.8491），证明这次改造是行为等价的替换，不是"看起来更好了"。

## 6. 已知取舍

1. **articles/laws 表保留不删**：它们仍是默认库的数据源与迁移输入，但检索层不再读。
   代价是"同一份数据存在两处"，README 需注明"articles 是默认库的迁移源"。
2. **documents 表没有 `(kb_id, source_law_id)` 唯一约束**：迁移脚本用"先查后插"保证不重复，
   属应用层约束；并发跑两次迁移理论上可能插重（演示规模可接受）。
3. **文档 id 不可预期**：serial 分配，测试里的失败插入（即使回滚）也会推进 sequence。
   故测试改为断言约束定义而非插非法值。
4. **内置法条 page 恒为 NULL**：法条没有页的概念，前端按"第 N 条"展示，不上页码。
