# 13 · 引用编号 [n] 与 snippet 字段

> V2.1 决策记录。对应 `app/agent/protocol.py`、`app/agent/state.py`、`app/agent/nodes.py`、
> `app/api/models.py`、`app/api/routes.py`、`app/static/index.html`、`tests/test_agent.py`、
> `tests/test_api.py`。格式约定（CLAUDE.md 第 6 条）。

## 1. 一句话结论

**答案里的引用从"自然语言点名（根据《劳动法》第 44 条）"升级为可点角标 `[n]`，
`done` 帧的引用从"只有定位信息"升级为"文档名 + 段号 + 截断片段 + 相关度"，
前端渲染成可展开卡片，点角标滚动并高亮对应卡片。**

## 2. 目标

- 用户能一眼看到"这句话的出处是哪一段原文"，而不只是"某法某条"。
- 引用可点击跳转，形成"答案 ↔ 来源"的双向对位。
- 老会话（改造前落库的引用格式）仍能正常回显。

## 3. 选中的方案

### 编号的唯一来源：检索顺序

`hits` 在 RRF/rerank 后已排好序，检索节点把**同一个列表**同时喂给 answerer 与 citations。
因此"第 i 个来源"与 `citations[i-1]` 天然对齐，不需要额外维护对应表。

`protocol.format_source_lines(hits)` 统一拼装，两套 LLM answerer 与离线模板共用：

```
[1] 《劳动法》第 44 条（第四章 工作时间和休息休假）：安排劳动者延长工作时间的……
[2] 《员工手册》第 12 段：……        ← 上传文档按"段"，内置法条按"条"
```

区分靠 `source_law_id`：有值=内置法条（第 N 条），无值=上传文档（第 N 段）。

### prompt 约束（两处 system prompt 同步）

> 引用规则（必须遵守）：每条结论后紧跟方括号编号标注出处，编号就是下方条文列表开头的
> 数字，例如「……应当支付经济补偿。[1]」。只能引用列表里出现过的编号，不得引用列表外的
> 来源，不得自造编号。

### 越界兜底：`scrub_citation_markers(text, max_n)`

LLM 偶尔会引用列表外的编号。纯函数正则抽取 `[n]`，**只删 n > max_n 或 n < 1 的**，
其余保留——即使 LLM 引错了具体哪一条，也比把整句角标抹掉更可读，而且"模型不听话"的
信号应该可见而不是被静默清理。离线模板同样走这条出口，保证行为一致、可测。

### API 字段（`CitationBrief`）

```python
kb_id, doc_id, doc_title, seq, page, heading,
snippet,          # 原文截断 300 字
score,            # 精排分优先，无精排时退融合分
source_law_id,
# 兼容老数据（V2.1 之前的 citations 只有这三个字段）
law_id, article_no, chapter
```

- **snippet 截断 300 字**：卡片只需让人判断"是不是这条"，不必把整段（甚至整页）塞进
  响应与历史记录。落库也存这个 brief，不再存整段原文——历史消息体积显著下降。
- **score 取精排分优先**：它更接近"对这个问题有多相关"；无精排时退融合分，
  前端统一显示"相关度 0.83"。
- **老字段保留为可空**：改造前落库的消息仍是 `{law_id, article_no, chapter, text}`，
  回读时前端走降级分支（`LAW_NAME` 映射 + 按"条"渲染）。

### 前端交互（`app/static/index.html`，零构建原生 JS）

- 答案文本渲染用 `renderAnswerText()`：**只把 `[n]` 变成可点 `<sup>`，其余一律
  `createTextNode`**——LLM 输出是不可信输入，绝不拼 `innerHTML`。
- 引用卡片 `attachCitations()`：`[n] 文档名 第 N 条/段 · 章名 · 相关度 0.83` + 片段。
- 点角标 → `scrollIntoView` 到对应卡片 + 闪一下（`.cit-flash`）。
- 流式期间是纯文本累积（打字机），`done` 帧收尾时再渲染一次升级角标。

## 4. 备选及为什么不选

| 备选 | 为什么不选 |
|---|---|
| 继续用自然语言引用（"根据《劳动法》第 44 条"） | 无法机器解析，做不了点击跳转；用户要自己在长答案里找对应关系 |
| 让 LLM 输出结构化 JSON 引用 | 流式输出下 JSON 不完整可解析性差；且把"引用来自检索结果"的确定性交给模型，等于放弃引用可靠性 |
| 用 `innerHTML` 渲染角标 | LLM 输出可能含 `<script>`，直接注入 XSS；`createTextNode` + 元素节点是唯一安全路径 |
| 引用卡片里放整段原文 | 响应与历史记录体积爆炸（一条法条几百字 × 8 条），且卡片本就要展开才看 |
| 编号由后端在答案里重新标注 | 需要把 LLM 的自由文本与来源对齐，比"让模型自己标 + 越界兜底"复杂且更不可靠 |
| 越界角标全部删掉（含 n≤max 的误引） | 会破坏答案可读性；且掩盖了"模型没按规矩引用"这一信号 |

## 5. 为什么这样最好

**引用不是 LLM 生成的，是检索命中的结构化字段**——LLM 只负责在正文里写编号。
这条边界让"答案里引的条文一定来自检索结果"成为架构保证，而不是提示词祈祷。
越界兜底只处理"编号写错"这一种失败模式，且失败可观测（决策 09 的拒答边界同理）。

## 6. 已知取舍

1. **编号可能"对错位"**：LLM 引用顺序不必与正文出现顺序一致，角标语义是"指向第 i 张
   卡片"而非"第 i 次出现"。只要模型按 prompt 用列表编号，就不会错位；越界兜底覆盖乱编。
2. **300 字截断可能截掉关键句**：卡片是"索引"不是"全文"，用户需要看全文时按文档名去查。
   将来可加"展开全文"接口按 `chunk_id` 取原文（当前不下发 chunk_id 给前端是刻意的，
   避免暴露内部 id 语义）。
3. **老数据不迁移**：历史消息里的引用仍是旧格式，前端降级渲染（显示"《劳动法》第 44 条"，
   无片段无分数）。不写数据迁移是因为旧格式信息量本就少，迁移不会让它变得更有用。
4. **`[n]` 与正文里原本出现的方括号数字可能误伤**：兜底只处理越界编号，正文里合法范围内的
   `[2024]` 之类不会被删（正则限 1–3 位且需在 1..max 内才保留）。实际语料中几乎不出现。
