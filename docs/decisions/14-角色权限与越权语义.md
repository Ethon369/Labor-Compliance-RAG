# 14 · 角色权限与越权语义

> V2.2 决策记录。对应 `app/api/deps.py`、`app/api/admin_routes.py`、`app/api/auth.py`、
> `app/kb/store.py`、`app/main.py`、`tests/test_admin.py`。格式约定（CLAUDE.md 第 6 条）。

## 1. 一句话结论

**两级角色（user/admin）+ 三层资源可见性：自己的 / 公开的 / admin 全见。
鉴权从"每个端点手动解析 token"升级为 FastAPI 依赖（`require_admin` /
`require_kb_access`）；越权时"看不到的资源返回 404、看得到但不能写返回 403"。
管理员账号由启动时幂等初始化，**不覆盖已改过的密码**。**

## 2. 目标

- 普通用户能管自己的知识库；公开库人人可问答、只有 owner/admin 可改。
- admin 额外能管全平台库与用户（列表/升降级/重置密码/禁用）。
- 越权行为要可测、语义要一致，且不泄露"某资源是否存在"。

## 3. 选中的方案

### 角色与账号

| 项 | 实现 |
|---|---|
| 角色列 | `users.role text NOT NULL DEFAULT 'user' CHECK (role IN ('user','admin'))` |
| 禁用列 | `users.disabled boolean NOT NULL DEFAULT false`（不删数据，只拒登录） |
| admin 初始化 | `ensure_admin(dsn, username, password)`：不存在则建号置 admin；已存在只补 role |
| 配置 | `ADMIN_USERNAME` / `ADMIN_PASSWORD`，默认 admin/123456，`.env.example` + README 双标注"演示凭据，生产必改" |

**为什么"已存在则只补 role、绝不覆盖密码"**：管理员第一次登录后通常会改密码。
如果每次重启都把密码打回默认值，等于把管理员账号变成公开后门——这是真实事故的常见成因。

### 鉴权落点（`app/api/deps.py`）

```python
get_current_user(request) -> CurrentUser(id, username, role)   # 401
require_admin(user = Depends(get_current_user))                 # 403
require_kb_access(write=False)  # 依赖工厂，读/写两种强度
```

- **为什么新路由用依赖、老路由不动**：`/admin`、`/kb` 端点数量多、规则统一，依赖让
  "鉴权"成为函数签名的一部分（漏写就报错），比"记得手动调一次"可靠。既有聊天路由
  保持手动风格，避免为重构而重构。
- **`require_kb_access` 是工厂函数**：读权限与写权限的判定只差一个条件，用参数区分，
  调用处写 `Depends(require_kb_access())` / `Depends(require_kb_access(write=True))`。

### 越权语义（本决策的重点）

| 场景 | 返回 | 为什么 |
|---|---|---|
| 未登录 / token 无效 / 账号被禁 | 401 | 认证层问题，语义统一 |
| 普通用户调 `/admin/*` | 403 | 身份已知，拒绝的是权限 |
| 访问他人**私有**知识库 | **404** | 返回 403 等于确认"这个库存在"，可被用来枚举他人资源 |
| 修改他人**公开**知识库 | 403 | 资源本就可见，拒绝的是写权限，404 反而误导 |

这条"404 vs 403"的分界是面试高频考点：**错误码本身也是信息泄露面**。

### 管理员接口（`app/api/admin_routes.py`）

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/admin/users` | 分页列表（新注册在前） |
| PATCH | `/admin/users/{uid}/role` | 升降级 |
| POST | `/admin/users/{uid}/reset-password` | 重置他人密码 |
| POST | `/admin/users/{uid}/disabled` | 禁用/解禁 |

两条**自锁保护**：管理员不能改自己的角色、不能禁用自己——否则一次误操作可能让系统
再无管理员可登录。禁用用户后，其已签发的 token 也会在下次请求时被 `get_current_user`
拒绝（每次请求都查库确认状态，而不是只信 token 里的 uid）。

### 改密码

`POST /auth/change-password`：验旧密码（错 → 400）→ 新密码至少 6 位（不足 → 422，
由 Pydantic 挡）→ 更新哈希。注册/登录/`/auth/me` 一并返回 `role`，前端据此决定是否
显示管理入口。

## 4. 备选及为什么不选

| 备选 | 为什么不选 |
|---|---|
| 用 JWT 存 role，请求时不查库 | 禁用/降级无法即时生效（token 有效期内一直是 admin）；本项目 token 是自制 HMAC，加 role 也只是把问题推迟 |
| 越权统一 403 | 会泄露"资源存在"这一事实，可被枚举 |
| 越权统一 404 | 对"公开库但非 owner"场景是误导：资源明明可见 |
| 删除用户代替禁用 | 级联删掉其知识库与会话历史，不可逆；禁用保留数据、可反悔 |
| 每个端点手动 `_bearer_user_id` | 新端点数量多，漏调一次就是越权漏洞；依赖注入让漏写变成启动/类型错误 |
| 单独的 RBAC 表（roles/permissions） | 两级角色、一个资源类型，引入 RBAC 表是过度设计（决策 09 同款判断） |

## 5. 为什么这样最好

**权限规则的复杂度应该匹配业务复杂度**：两级角色 + 三类可见性，用两个依赖函数表达
就够了；等真出现"团队/协作者/只读成员"时再谈 RBAC。同时把**越权语义写成可执行的测试**
（`tests/test_admin.py` 15 个用例覆盖 401/403/404 三种分界与自锁保护），
让"安全"从口头承诺变成回归测试能守住的东西。

## 6. 已知取舍

1. **管理员不是"超级用户"的细粒度控制**：admin 能改所有库、重置所有人密码，没有操作审计。
   演示规模够用；真要追责需要 `audit_log` 表（未做）。
2. **禁用只挡新请求，不主动踢掉在线连接**：SSE 长连接已建立的仍会跑完当前问答
   （下次请求即被拒）。主动踢需要连接注册表，暂不做。
3. **重置密码后旧 token 仍有效**：token 无状态、无吊销列表（决策 10 已记）。
   要即时失效需要引入 Redis 黑名单或短 TTL + refresh token。
4. **`require_kb_access` 在 V2.2 尚无路由使用**：它随 `/kb` 端点一起在 V2.3 接入并补
   端到端越权测试；本阶段先由 `tests/test_admin.py` 覆盖 `require_admin` 的三种分界。
