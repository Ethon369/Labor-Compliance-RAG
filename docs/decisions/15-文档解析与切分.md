# 15 · 文档解析与切分

> V2.3 决策记录。对应 `app/kb/parser.py`、`app/kb/splitter.py`、`tests/test_parser.py`、
> `tests/test_splitter.py`。格式约定（CLAUDE.md 第 6 条）。

## 1. 一句话结论

**上传文件先经 `parser` 解析成带"页码 + 是否标题"的 `Block` 流，再由 `splitter`
递归切成不超过 `chunk_size` 的片段；两条不可妥协的契约——每片长度 ≤ chunk_size、
不劈开句子。标题识别是 parser 的职责，splitter 只消费 `is_heading`，两阶段职责分明、
各自可独立测试。**

## 2. 目标

- 支持 pdf / docx / txt / md 四种格式，统一转成内部 `ParsedDoc`（Block 流）。
- 切分要尊重语义边界：能按段切就按段、按段超长退句子、句子仍超长才硬切。
- 切分参数随知识库走（`kb.chunk_size` / `chunk_overlap`），换库即换粒度。
- 扫描版 PDF 等"能开但取不到字"的情况要可识别、可提示，而不是静默产出空库。

## 3. 选中的方案

### 两阶段职责划分

| 阶段 | 模块 | 输入 → 输出 | 职责 |
|---|---|---|---|
| 解析 | `parser.py` | 文件路径 + 类型 → `ParsedDoc`（Block 流） | 识别来源格式、判断标题、带页码 |
| 切分 | `splitter.py` | `ParsedDoc` → `list[TextChunk]` | 只消费 `is_heading`，按语义边界切段 |

**为什么"标题识别归 parser、splitter 只消费标记"**：标题在不同格式里长得不一样——
Markdown 是 `#` 前缀、docx 是 heading 样式、txt 只能靠正则启发式（如"第 X 章"）。
让 splitter 去理解来源格式，就会把"格式差异"泄漏进"切分逻辑"，两种职责纠缠后
既难测试也难扩展新格式。parser 统一把"这里是不是标题"沉淀成一个布尔标记，
splitter 只需回答"标题该不该撑起一个新段"。

### 解析细节

- **编码回退**：txt 先按 `utf-8` 读，失败回退 `gb18030`。中文老文档大量是 GBK 编码，
  直接 utf-8 会在第一行就崩。
- **扫描件识别**：pdf 打开后取不到文字层 → 抛 `UnsupportedContentError`（不是 `Exception`
  子类的通用错误，是专门的"这不是系统故障"信号），调用方标 `failed` 并提示用户。
  OCR 明确不做（见 §4）。
- **页码**：pdf 按页产出 Block、docx 按段落产出，都带上页码/段落序号线索，供引用卡片
  显示"第几页/第几段"。

### 切分算法（`split_document`）

1. **按标题切段**（`_sections`）：标题 Block 撑起一个新的 section，其下正文归入该段，
   片段携带"最近上级标题"作为 `heading`（Markdown 的 `#` 前缀在 heading 字段里被剥掉，
   正文保留原样）。
2. **原子化**（`_atomize`）：段内先按段落切；段落超长退到按句子切；句子仍超长才硬切。
   逐级退让，尽最大努力保住语义边界。
3. **硬切用均分而非"切满再留残片"**（`_hard_cut`）：250 字切 100，逐块切满会得到
   100/100/50，均分得到 84/84/82——片段长度越均匀，检索的召回越稳定，也避免最后
   一片过短沦为噪声。
4. **贪心合并 + overlap 尾缀**（`_merge`）：把原子片段按 `chunk_size` 贪心合并，并在
   片间补 `overlap` 个字符的尾缀，保证跨片边界处的语义不因切断而丢失。

**两条契约（写进测试）**：每片 `char_count ≤ chunk_size`；不劈开句子（句子级切分是
硬切之前的最后一道防线，硬切只发生在单句本身超长时）。

## 4. 备选及为什么不选

| 备选 | 为什么不选 |
|---|---|
| 固定长度切分（每 500 字一刀） | 会劈开句子/段落，引用片段读到一半戛然而止；语义碎片化直接损害检索质量 |
| splitter 内嵌各格式标题正则 | 格式差异泄漏进切分逻辑，两职责纠缠难测试；新增格式要改切分器 |
| 扫描版 PDF 上 OCR | 需要引入 OCR 引擎（重依赖、慢、准确率依赖训练集），演示规模价值低；README 注明"扫描件不支持"即可 |
| 用 sha256 做内容指纹 | 这里只做"内容变没变"的等值判断，不是密码学用途；md5 更快且够用（`hash_content`） |
| 切分参数读全局配置 | 不同知识库粒度需求不同（法条要短、合同要长），参数随库走才灵活 |

## 5. 为什么这样最好

**把"解析"与"切分"拆成两个纯函数**，各自输入输出都是可构造的普通数据（文件路径 /
Block 流），于是两个模块各有一组不碰数据库、不碰网络的单元测试（35 个用例），
覆盖编码回退、空文件、标题识别、超长句子硬切、overlap 合并等边界。这正是"可测试性"
反过来倒逼设计：如果当初图省事把解析和切分揉成一个函数，这些边界要么测不到、
要么测起来要 mock 一堆文件系统。

## 6. 已知取舍

1. **片跨页只记起始页**：一个片段若横跨两页，`page` 只记它从哪页开始。对引用定位
   已经够用；要精确到"每个字符在哪页"需要存字符级偏移，收益低、存储大，不做。
2. **扫描版 PDF 不支持**（无文字层）。README 与上传提示都写明；要支持需引入 OCR。
3. **docx 的表格/图片不解析**：只取段落文本。表格里的法条内容会被漏掉——如果某库
   大量依赖表格，需另加表格提取逻辑（当前未做）。
4. **md 的标题识别靠 `#` 前缀启发式**，不做 CommonMark 全量解析；够用且零依赖。
