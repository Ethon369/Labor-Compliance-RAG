# 17 · 连接池与 HNSW 向量索引

> V2.4 决策记录。对应 `app/core/db.py`、`scripts/ensure_hnsw.py`、`tests/test_db.py`、
> 以及 `app/api/auth.py` / `app/kb/store.py` / `app/rag/vectorstore.py` 的短连接替换。
> 格式约定（CLAUDE.md 第 6 条）。

## 1. 一句话结论

**把"每次查询开一条短连接"替换成 `psycopg_pool` 按 dsn 缓存的连接池——全量测试耗时
从 21.6s 降到 6.6s、纯向量检索延迟压到 ~1.3ms；同时给 chunks 建了幂等的 HNSW 向量
索引，用 EXPLAIN 和评测集双向验证：召回无损（四个基线数字逐位不变），但当前 517 片
规模下优化器仍选择顺序扫描——索引是"为规模化预留的加速开关"，不是此刻的收益点。**

## 2. 目标

- 消除"每条 SQL 都建连 + 握手 + 认证 + 后端 fork"的最大延迟来源。
- 给向量近邻检索加上规模化后能用得上的索引，且不能以召回退化为代价。
- 两项都要可量化验证，而不是"改完说更快了"。

## 3. 选中的方案

### 连接池（`app/core/db.py`）

| 设计点 | 实现 |
|---|---|
| 池缓存 | `dict[dsn → ConnectionPool]` + 双重检查锁；同 dsn 只建一个池 |
| 池上限 | `POOL_SIZE = 8`（≥ 并发问答线程数 + 上传并发） |
| 懒建 | `open=False` 后首次调用 `open()`，配合懒加载 |
| 超时 | `timeout=30s`：池满时 `connection()` 最多等 30 秒，不无限挂起 |
| 上下文 | `pool_conn(dsn)` 的 `with` 语义与 `psycopg.connect` 对齐（正常提交/异常回滚） |

**为什么按 dsn 缓存而不是全局单池**：测试用不同 dsn 连不同临时库，单池会串库。
生产只有一条 dsn，退化为单池，行为一致。

**替换范围**：`auth.py` / `kb/store.py` / `kb/schema.py` / `vectorstore.py` 共 30 余处
`psycopg.connect(...)` 全部换成 `pool_conn(...)`，事务语义不变，调用方零改动。

**量化收益**（真实数据）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 全量 264 测试耗时 | 21.6s | **6.6s**（-70%） |
| `vector_topk` 平均延迟 | 每次含建连 | **~1.3ms**（100 次均值） |

### HNSW 索引（`scripts/ensure_hnsw.py`）

`CREATE INDEX chunks_embedding_hnsw ON chunks USING hnsw (embedding vector_cosine_ops)`，
m=16、ef_construction=64（默认值，数据量小不必调参）。

**为什么是独立脚本而非塞进 `ensure_ready()`**：建 HNSW 是有代价的运维动作——近似索引
数据量小时可能略降召回、建索引本身锁表耗时。它不该在应用每次启动时悄悄做，而应由人
显式触发、跑完评测确认召回没退化再上线。脚本幂等（查 `pg_indexes`），可反复跑。

## 4. 备选及为什么不选

| 备选 | 为什么不选 |
|---|---|
| 每次查询继续开短连接 | 延迟叠加是最大瓶颈；实测池化后测试耗时降 70% |
| 单池（不按 dsn） | 测试多临时库会串库 |
| 池上限设很大（如 100） | 单 worker + 有限并发下 8 够用；更大要先评估 PG `max_connections` |
| HNSW 建索引塞进 `ensure_ready()` | 让"可能降召回的近似索引"在启动时悄悄生效，不可控 |
| IVF 索引代替 HNSW | IVF 需要训练步（`lists` 划分），且召回对 `probes` 敏感；HNSW 无训练、调参少 |
| 因为"索引没被采用"就不建 | 索引是数据规模函数：万级片才走索引。现在建好、脚本幂等，规模化后跑一次即生效，且已用评测集证明召回无损 |

## 5. 为什么这样最好

**用证据代替"感觉"**。连接池的收益有前后测试耗时对比；HNSW 的"当前不生效"结论有
两重证据——EXPLAIN 显示优化器选 `Seq Scan`（全表扫 cost 34.23 低于索引扫描），评测
四个数字逐位不变证明召回无损。这两件事在面试里都成立："我做了池化，量化了收益"，
以及"我建了 HNSW，但用 EXPLAIN 发现 517 片规模下优化器不采用它，于是我把它定位成
规模化预留的加速开关，而不是假装它现在就在提速"——后者比堆组件更显成熟。

## 6. 已知取舍

1. **HNSW 当前不生效**：`EXPLAIN` 确认 517 片、`kb_id` 过滤后 164 行匹配时，优化器
   选择顺序扫描。索引的价值要到数据量到万级才体现（这是 pgvector 的已知成本模型）。
2. **HNSW 是近似索引**：即使将来走索引，极端 case 下 top-k 可能与精确扫描有细微差异。
   决策 13 的评测基线是"召回不退化的验收线"，规模化后需重跑确认。
3. **连接池不跨进程**：`psycopg_pool` 是进程内池；多 worker（多进程）时每进程各有一个
   池，PG 侧要相应预留 `max_connections`。当前单 worker 不涉及。
4. **池没有自动重连健康检查**：`psycopg_pool` 默认对坏连接做惰性剔除，但极端网络抖动
   下首个请求可能碰到失效连接。演示规模可接受；生产可加 `check=ConnectionPool.check_connection`。
5. **临时表测试的教训**：池复用下两次 `pool_conn` 可能拿到不同物理连接，`TEMP TABLE`
   跨连接不可见——这本身印证了复用，也提醒测试别依赖连接会话态。
