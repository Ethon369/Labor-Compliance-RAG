# 18 · 性能工程收口（GZip/静态缓存/限流/分页/观测/并发/嵌入去重）

> V2.4 决策记录。对应 `app/core/ratelimit.py`、`app/main.py`（GZip/静态缓存/X-Request-Id/
> 线程池）、`app/api/routes.py`（分页 + done 帧耗时打点）、`app/kb/pipeline.py`（嵌入去重）。
> 格式约定（CLAUDE.md 第 6 条）。连接池与 HNSW 见决策 17。

## 1. 一句话结论

**在不新增依赖（连接池除外）的前提下，做了一组"性价比高、收益明显"的性能与工程
收口：GZip + 静态长缓存降传输、内存令牌桶限流 + 登录失败小窗口防刷防爆破、列表统一
page/page_size 分页、X-Request-Id + done 帧耗时打点做观测、线程池替代裸线程、嵌入
去重复用未变切片向量——每一项都有测试或冒烟验证，且不碰检索内核、评测基线逐位不变。**

## 2. 目标

- 传输层省流量：静态资产长缓存、大响应 GZip。
- 安全层防刷：问答/注册/上传限频，登录防爆破。
- 工程层提效：列表分页不再硬编码 limit；请求可追踪（X-Request-Id）；耗时可观测。
- 并发层可控：线程池复用替代每请求裸开线程。
- 嵌入去重：重传/重处理时内容未变的切片复用旧向量，省 embedding 调用。

## 3. 选中的方案

### GZip + 静态缓存（`app/main.py`）

- `GZipMiddleware(minimum_size=1024)`：只压 >1KB 响应，小响应压缩收益低还费 CPU。
- `CacheStaticFiles`：StaticFiles 子类，按扩展名给 `.js/.css/.png/.svg/.woff2` 加
  `Cache-Control: public, max-age=86400`；html 不缓存，保证页面/接口始终最新。

### 限流（`app/core/ratelimit.py`）

| 能力 | 实现 | 参数 |
|---|---|---|
| 令牌桶 | `TokenBucketLimiter.allow(key, capacity, refill)`，按 (端点, IP) 分桶 | — |
| 注册限频 | `rate_limit(5, 1/60)` | 5 次/分钟，防脚本刷号 |
| 问答限频 | `rate_limit(30, 1/2)` | 30 次/2 秒，防重路径被刷 |
| 上传限频 | `rate_limit(10, 1/60)` | 10 次/分钟，防重写路径被刷 |
| 登录防爆破 | `LoginGuard`：同 IP 连续失败 5 次封禁 60 秒 | 成功即清零 |

**为什么登录单独一层 `LoginGuard`**：普通令牌桶防的是"高频合法请求"，防爆破要的是
"失败次数的滑动窗口"，语义不同不能复用同一个桶。成功后 reset，避免把用户偶发失败
累积成误封。

**为什么内存而非 Redis**：单 worker 演示规模，内存桶零依赖、判定 O(1)；多 worker 才
需要跨进程共享计数（Redis）。判定独立成纯函数，将来换 Redis 只改这一层。

### 分页（`app/api/routes.py`）

`/chat/sessions`、`/chat/history`、`/chat/history/mine` 从 `limit` 硬编码改成
`page/page_size`（默认 1/50，上限 100），返回 `{records, total, page, page_size}`。
kb 文档列表与 admin 用户/库列表此前已分页，这里对齐签名。

### 观测（`app/main.py` + `routes.py`）

- `X-Request-Id` 中间件：透传上游 id，没有则生成；响应头回显。一条请求的检索/LLM/DB
  各段耗时靠同一个 id 串起来定位。
- `done` 帧新增 `elapsed_ms`（整条 SSE 链路）与 `graph_ms`（检索+生成图执行）：
  让"这条问答到底花了多久"可观测，前端默认忽略，需要时读。

### 并发模型（`app/main.py`）

lifespan 建 `ThreadPoolExecutor(max_workers=4, thread_name_prefix="chat")`，
`_stream_chat` 用 `loop.run_in_executor(executor, run_graph)` 替代 `threading.Thread`。
线程复用、并发上限可控；executor 为 None 时退回裸线程（测试/离线路径）。

### 嵌入去重（`app/kb/pipeline.py`）

写前查 `store.doc_embedded(doc_id)` 得 `{seq: (content_hash, embedding_text)}`，
对每个切片：`(seq, content_hash)` 都匹配 → 复用旧向量（`parse_vector` 解析），
否则重新 embed。收益随重传/重处理频率放大。

**顺带修了一个真 bug**：原 `kb_row.get("chunk_overlap") or 80` 会把合法的 `chunk_overlap=0`
（不重叠）误判成"未设置"覆盖成 80——`0 or 80` 的 falsy 陷阱。改成 `is not None` 判断。
这正是"写测试倒逼发现边界"的典型例证。

## 4. 备选及为什么不选

| 备选 | 为什么不选 |
|---|---|
| 限流用 Redis | 单 worker 内存桶够用；多 worker 才需要共享计数 |
| 限流阈值写死 | 参数以 `rate_limit(capacity, refill)` 工厂注入，调用处可调；写死难调优 |
| 静态缓存全文件一刀切长缓存 | html/接口不能缓存，否则改版后浏览器拿旧页 |
| 分页用 `limit/offset` 参数名 | 与 kb/admin 已有的 `page/page_size` 不统一；统一后前端心智一致 |
| 各段耗时用节点级打点 | 需侵入 agent 内核（违背"内核不动"原则）；总耗时 + 图耗时已够观测 |
| 嵌入去重跨文档匹配 | 数据模型里 chunk 归属 doc，跨 doc 匹配要全局 (content_hash) 索引，复杂度高、收益低 |
| 嵌入去重用 `or 默认值` 取切分参数 | 是 bug：`0 or 80` 把合法值 0 吃掉，见 §3 |

## 5. 为什么这样最好

**每一项都有验证、且不碰核心**。GZip/缓存/X-Request-Id 用冒烟请求验证头字段；限流
有纯单元测试（令牌桶容量/补充/隔离、LoginGuard 封禁/清零）；分页有 API 测试；
嵌入去重有"全量复用 embed 调用为 0"与"部分变化只重算变化切片"两个集成测试；评测
基线逐位不变证明检索内核未受影响。这套"做一项、验一项、不碰核心"的节奏，正是
"知道何时不做"的延续（决策 06/16 同款判断）——Redis、节点级打点、跨文档去重都
明确评估过并记为"不做"。

## 6. 已知取舍

1. **限流是内存态、单进程**：多 worker（多进程）下各进程独立计数，限流会被"稀释"。
   单 worker 演示规模无感；要严格限流需 Redis 计数器。
2. **`client_ip` 信任 `X-Forwarded-For`**：本地直连取 peer；若未来上反向代理，需按
   "可信代理层"重写，否则攻击者可伪造该头绕过限流。
3. **`X-Request-Id` 未接入日志**：当前只在响应头回显，没把 id 打进结构化日志。
   真正串联各段耗时需配合 logging 的 request_id 字段（未做，观察规模够用）。
4. **线程池 4 worker 是拍脑袋值**：依据是"检索+LLM 是 I/O 密集、CPU 轻"。
   真实上限要压测；uvicorn 单 worker 下 4 已够演示并发。
5. **嵌入去重只在同 doc_id 内生效**：文档重传走新 doc_id，不会复用旧向量（数据模型
   限制，见 §4）。真正的重传去重需跨 doc 的 content_hash 索引。
